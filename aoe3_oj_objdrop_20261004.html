OJ「所有资源均不动」——第二层根因：HumanAction 的 obj 判据

提交 6204 复盘 ｜ 引擎 v3.0.7h ｜ 对照：本机 7g / 7h × -exam/非-exam 四种组合 ｜ 2026-10-04
一句话：不是引擎拒收指令，也不是「AI 没下指令」——是 AI 每帧为 全部 12 个村民下发的 INS_HUMANACTION（设置工作目标），在帧末提交体检里被 100% 丢弃；引擎一条都收不到，所以资源 33 分钟一动不动、祭司站桩被打死。

一、断点定位：自检有两层，上轮只拆了第一层

commitInstruction() 提交前逐条体检两个裸指针，两层是串联的：

// ① self（执行者）——上一轮已放宽为「以权威表当前值为准」
Coordinate* curSelf = resolveSelfCurrent(c);
if (!curSelf) { 丢弃; continue; }              // 键不存在 / 值为 NULL
if (curSelf != c.self) { 采用当前指针; }        // ← 上轮的修法

// ② obj（工作目标）——本轮才发现它仍要求「逐字节相同」
if (c.type == INS_HUMANACTION) {
    if (it == end() || it->second != c.obj) { 丢弃; }  // ← 上一轮的旧口径，未被 ① 覆盖
}

评测机日志（提交 6204）的数值形状把这两层的先后关系钉死了：

[INS-DIAG f=12]   n=12  drop=9(noKey=0 nullSelf=3) adopt=8   objNull=3
[INS-DIAG f=1500] n=9   drop=9(noKey=0 nullSelf=0) adopt=9   objNull=0
[INS-DIAG f=3000] n=12  drop=12(noKey=0 nullSelf=0) adopt=12  objNull=0  前4=(2,41159>..)(2,41124>..)(2,41146>..)(2,41135>..)

noKey=0 / nullSelf=0 ⇒ ① 不再丢任何一条（上轮修法生效）；drop 却仍等于 n ⇒ 丢弃全部来自 ②。 而 前4 全是 type=2（INS_HUMANACTION，见 config.h:646）⇒ 被丢的就是村民工作令。

三、本轮改动（已编译进提交件）

1. ② obj 与 ① self 统一口径（核心修复）

旧口径 it->second != c.obj 要求「帧末的表值」与「构造时的副本」逐字节相同——这比引擎自己还严。 引擎执行时用的是 Core.cpp:1394 的 Coordinate* obj = cur.obj;，存在性闸只有 obj == NULL || g_Object[cur.obSN] == NULL（Core.cpp:1395），从不比对副本。 新口径：键不存在 ⇒ 丢；值为 NULL ⇒ 丢；键存在且非空 ⇒ 把当前权威指针填进 c.obj（引擎随即用的就是这个对象）。

2. 三行自证心跳（无论有无丢弃都打；这是下一版日志的判读依据）

[INS-DIAG f=%1] n= gObj= drop=(noKey= nullSelf=) adopt= objNull= 前4=(type,SN>obSN)
[INS-SEG  f=%1] null= 4= 5= 2= 9= 1= O= objMiss=(SN>obSN)...
[INS-PTR  f=%1] objMoved= objNoKey= objIsNull= objDropNull= [SN= self= now= | obSN= obj= nowO=]
  • 前4 现在是 (type,SN>obSN)：直接看到「谁给谁下令」——本机实测 (2,41135>50201)＝村民 41135 去砍树 50201。
  • INS-SEG 按 globalNum/10000 给 g_Object 分段：4=我方单位 5=树/动物 2=浆果金矿石矿 9=我方军事 1=敌 null=值为 NULL 的键。
  • INS-PTR 打印十六进制地址：self/now 与 obj/nowO 是否同一地址，一眼可判「指针被更新」还是「对象已换」。
