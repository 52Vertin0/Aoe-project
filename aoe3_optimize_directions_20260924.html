AoE3 UsrAI 优化方向

基于「群内快速升级/造兵打法」逐条对照现行代码（UsrAI.cpp 2710f75b / 6622 行）　·　2026-09-24
一句话结论
挖到了 8/8 负局完全同形的死因：祭司在反攻期主动前出去感化战车弓兵/战车/阔剑兵，起手后 54~535 帧（2~21 秒）内被打死；而 3/3 胜局的祭司最后感化目标都是攻城武器厂。
根因不是新 bug，是两套互斥逻辑打架：managePriest() 的「能感化直接感化（无任何门槛）」每帧先跑并 return，把 manageCounterAttack() 里「祭司保持在大队后方 PRIEST_SAFE_BEHIND 格」的安全设计永久屏蔽。

二、根因解剖：谁在每一帧说话

2.1 调用顺序决定谁能生效

processData() 每帧的调用链（UsrAI.cpp:525）：

0 handleBuildResults()→ 1 checkDefeat()→ 3 managePriest()→ 5 updateState()→ 7 manageEconomy()→ 8 manageMilitary()→ 9 manageCounterAttack()

第 3 步在第 9 步之前，而第 3 步里的感化档命中就 return。这不是"优先级"，是"垄断"。

三个要点：

  • 无位置门槛：不看祭司当前在哪、前方有没有己方军队。
  • 无兵力门槛：不要求目标附近有我方保护兵力。
  • 会主动前出：cdist > 12 格 时调 priestApproachMove() 走过去 —— 搜索半径是 PRIEST_CONVERT_RANGE，实测值 28.0 格，意味着祭司愿意为够一个目标主动前进最多 28 格。

致命的射程算术
祭司感化距离 = 12 格（DIS_PRIEST=12）；战车弓兵射程 = 7 格。
祭司要够到一辆战车弓兵，必须走进 12 格 —— 而 12 > 7，意味着它必然同时进入对方射程。若旁边还有敌方复合弓兵（射程 7）护卫，那就是走进一片交叉火力。
实测 cur2：起手（f=39806）→ 敌复合弓兵/战车弓兵同帧锁定祭司（f=39836，30 帧后）→ 祭司死亡（f=39894，共 88 帧 = 3.5 秒）。

2.4 三个常量在数值上直接打架

常量值语义定义处
PRIEST_CONVERT_RANGE28.0 格感化目标的搜索半径（够不着就主动走过去）UsrAI.cpp:304
PRIEST_MIN_DIST_TARGET18.0 格祭司与反攻目标的最小安全距离UsrAI.cpp:344
PRIEST_SAFE_BEHIND8.0 格祭司应位于大队身后的距离UsrAI.cpp:308
28 > 18：安全区被搜索半径整个吞掉
「保持 ≥18 格才算安全」是第 9 步的意图；「28 格内都能搜到并主动走过去」是第 3 步的实现。
28 > 18 ⇒ 祭司站在被判定为"安全"的位置（25 格）时，依然能搜到一个 28 格外的战车弓兵，然后主动前出 13 格 —— 一举跨进安全区以内，还顺带进了对方 7 格射程。

另注：managePriest() L1246 的注释写的是「视野内有可感化敌(≤20格)」，与常量的 28.0 不符 —— 属陈旧注释。这条是 2026-09-23 那轮注释审计的漏网之鱼，因为它在讨论逻辑时一直被当作事实引用（本轮就是差点采信它）。

bool priestTooClose = (pDist < PRIEST_MIN_DIST_TARGET * BL);
...
// ★ 祭司跟随【己方大部队重心】(排除自身)，始终位于大队【后方】(朝 TC 方向) PRIEST_SAFE_BEHIND 格，

这段的意图与需求完全正确 —— 但它躺在第 9 步里，而祭司在第 3 步就已经被支配了。只要第 3 步的 safeConv >= 0 成立（反攻期敌方军队遍地，几乎恒成立），第 9 步的祭司分支连一行都跑不到。

根因一句话
「无门槛感化」与「安全距离」是同一个祭司的两套控制器，谁先 return 谁说话。 现行代码里前者每帧先说话，所以后者是死代码 —— 这也解释了为什么 2026-09-12 那次"祭司反攻不要太靠前"的改动看起来生效了但实际上没有收益。

三、优化方向（按 收益 ÷ 成本 排序）

P0 反攻期禁止祭司感化「远程兵」 成本 ≈ 6 行　收益 高　风险 低

证据6/8 负局的最后感化目标是战车弓兵；胜局无一例外都是武器厂。 改法给 findConvertTarget 增加一个"是否允许远程档"的开关（默认 true 保持既有行为）；managePriest() 在 state == COUNTERATTACK 时传 false，即第③档「远程军队」整档跳过，落到第④档投石车/兜底村民。
更保守的变体：只排除「战车弓兵 / 复合弓兵 / 弓兵 / 投石兵」这几个射程 ≥ 4 格的兵种，保留投石车（走得慢，攻略也说"可以最后处理"）。 为什么有效直接砍掉"祭司主动走进敌方远程火力网"这个动作本身，不依赖任何后续补偿逻辑。 风险低。副作用 = 反攻期祭司对敌方远程兵的压制力下降；但攻略明确指出祭司的活是"转变方阵兵"和"最后感化武器厂"，远程兵本不该由祭司处理。 验证跑 12 局，看两点：① _priest_death.py 里负局的最后感化目标不再出现远程兵；② 祭司死亡帧从 37xxx 推迟或消失。中位死亡帧后移即可判定方向正确。

P0 的落地骨架（可直接实现）

// ① findConvertTarget 尾部增一个开关参数，默认值保证既有 3 处调用点行为逐字不变
auto findConvertTarget = [&](double dr, double ur, double range,
                             bool allowRanged = true) -> int {
    int t;
    if ((t = pickByBlood(0)) >= 0) return t;   // 方阵兵 —— 永远允许
    if ((t = pickByBlood(1)) >= 0) return t;   // 其余近战 —— 永远允许
    if (allowRanged && (t = pickByBlood(2)) >= 0) return t;   // 远程军队 ← 反攻期关掉
    if ((t = pickByBlood(3)) >= 0) return t;   // 投石车：射程 10 < 感化距离 12 ⇒ 够得着且不被还手，保留
    /* 兜底：最近敌方村民 —— 保留 */
};

// ② 调用点（managePriest 的感化检测处，UsrAI.cpp:1250）
bool allowRanged = (state != COUNTERATTACK);   // 仅反攻期生效，前两波行为不变
int t = findConvertTarget(pDR, pUR, PRIEST_CONVERT_RANGE * BL, allowRanged);

为什么保留投石车档：投石车射程 10 格 < 祭司感化距离 12 格 ⇒ 祭司能在对方够不着的 12 格边界上感化它，是安全的（且攻略也说"投石车走得慢、不构成直接威胁，可以最后处理或转来自己用"）。要排除的是射程 7 格的战车弓兵/复合弓兵这一档。

P0b 给祭司前出加「兵力门槛」 成本 ≈ 15 行　收益 高　风险 中

攻略原文「祭司抵达集结区域（为了安全可以放在集结区域离敌人最远的一格），周边有足够兵力，就可以进攻了。」 改法在 managePriest() 的感化档里，对"需要前出"的情形（cdist > 12 格，即要主动移动过去）追加门槛：该目标 12 格内我方非祭司军事单位 ≥ N（建议 2~4，先取 2 试）。不满足则该帧不起手，落到下方保命/待命逻辑。已在 12 格内的被动感化不受限。 代价若门槛过高会让祭司在反攻期几乎不感化（现有 N-2 的另一面）。 风险中。建议 N 从 2 起，跑批后按"祭司感化次数 vs 死亡帧"双向调参。 注意这一条与 P0 有重叠但不等价：P0 管"不许碰远程"，P0b 管"没有兵就别过去"（近战目标也可能在敌远程掩护下）。cur8 的最后目标是阔剑兵（近战）却仍死 —— 那条正是 P0b 要治的。

P1 让 manageCounterAttack() 的祭司安全逻辑真正生效 成本 ≈ 3 行　收益 高　风险 中

改法在 managePriest() 感化档之前加状态守卫：if (state == COUNTERATTACK) { /* 祭司交给 manageCounterAttack 的推进/后撤逻辑 */ } —— 用一个变量显式 fork，而不是让它自然 return。 语义这才是 2026-09-12 那次改动的本意。等于把两套控制器合成一套，消除"死代码"。 风险较高。反攻期祭司会改由 manageCounterAttack() 全权管理，而那套逻辑包含"非清场期退回大队后方"——可能导致祭司再也不主动感化，武器厂起手率从 3/12 掉到 0。历史上有前车之鉴（ALL WAVES 后祭司两头不管、被贴脸也不动的 bug）。 建议先做 P0 + P0b，观察一批后再决定是否动这条。P0/P0b 是"局部加闸"，这条是"换控制器"，风险和收益都大一个量级。

P2 我方复合弓优先打「锁定祭司的敌远程」 成本 ≈ 20 行　收益 中　风险 低

攻略原文「战斗时连打带射，复合弓优先攻击范围内的远程兵，以免祭司被打。」 现状已有"有敌人以祭司为目标 → 全军扑上拉仇恨"的分支（UsrAI.cpp:4011，判据 e.WorkObjectSN == priestSN），但它是全军一刀切：所有兵都去扑同一个仇恨目标，没做兵种分层。 改法在该分支内对复合弓兵/远程兵加一层优选：优先选敌方远程兵（战车弓兵/复合弓兵/弓兵/投石兵）作为目标；没有远程时再退化为原逻辑。 为什么有效这是"疏"而非"堵"：P0 让祭司不去惹远程，P2 让远程先死。两者互补。 风险低。可复用现有 sortIsRanged()，无新常量。

P2b 我方箭塔索敌改为「打没在打我的兵」 成本 ≈ 12 行　收益 中　风险 低

攻略原文「遍历箭塔周边 7 格内的敌军，如果敌军的目标不是自己（箭塔），则攻击敌军。如果敌军目标设为自己了，切换攻击目标为不是自己的敌军……这样祭司站在箭塔附近，只会被远程攻击。」 现状已实现手工索敌（UsrAI.cpp:3889 B 段，用 HumanAction(塔SN, 目标SN)，判据 Project != -1 为"已在攻击"）。但：
① 目标选取是"射程内最近敌人"，不看敌军当前锁定谁；
② if (tower.Project != -1) continue; —— 塔一旦锁定目标就不再换，直到目标死亡或离开。 改法① 目标筛选改为两档：优先 e.WorkObjectSN != tower.SN（没在打我的）中最近者；无则退化为最近者。
② 把 Project != -1 → continue 改成"仅当目标仍在自己射程内才跳过"，允许中途改打更该打的兵。 收益场景有效载荷 = 把塔的火力从"本来就跑不掉、正在拆塔的近战兵"转到"正在追祭司/农民的兵"。第一二波尤其值钱。 风险低。但要注意别让塔每帧改目标（加节流），否则引擎侧可能反复重置攻击前摇。

P2c 集结区从「单点」改成「5×5 区块循环填入」 成本 ≈ 25 行　收益 中　风险 低

攻略原文「单一集结点对于集结是不够的。因为核心有个特性，位置附近站满人则认为不可达，发命令人不动。因此需要一个集结区域，以集结点为中心，弄个 3*3-5*5 的区块，每个点去一个兵。攻击开始后，军队会移动，集结点就空出来了，可以循环填入。」 现状rallyCtrDR/UR 是单一坐标（TC 中心，UsrAI.cpp:4767）。（注：代码里已有一处"8/11/14 格 × 8 角 = 24 档"的散开逻辑，但那是"回基地外围待命螺旋"，不是集结区。） 改法把集结落点从 rallyCtrDR/UR 换成"以它为中心的 5×5 格阵列，按单位 SN 取格"。可以直接复用现成的散开写法（UsrAI.cpp:3945 那段 SN%11/SN%5 的做法）。 为什么有效这是引擎级的"拥堵判定"补偿，成本很低。攻略作者把它当必需项，说明实战差异明显。 风险低（只动落点、不动决策）。

P3 反攻时点前移 成本 ≈ 1 行　收益 高　风险 高

现状updateState() 进 COUNTERATTACK 的条件：frame > COUNTER_ATTACK_FORCE_TIME(33000) 且（敌数 < 3 或 frame > 39000）。实测反攻帧 12/12 恒为 33001 ⇒ 实际生效的是超时强制，第三波"全灭"条件从未提前满足。 攻略的时点「第二波防御一过就集结，集结 10 个左右复合弓就可以开战了，差不多是11 分钟多点」；「一般在防御过第三波之后，24000 帧左右（16 分钟）」。 差距我们 22 分钟开战 → 胜局耗时 39114 / 43001 / 44406 帧（26~30 分钟）。攻略理想线 27000 帧（18 分钟）胜。时间差 ≈ 6 分钟，几乎全部来自这里。 为什么难2026-09-08 有过明确教训：强制反攻阈值从 27000 上调到 33000，正是因为"armyCount 远未达 12 即提前全军出击、零散士兵 + 祭司被集火送命"。 建议不要一次跳。先只用 P0/P0b/P2 把祭司的存活率提上去，再看能否把 COUNTER_ATTACK_FORCE_TIME 从 33000 分两步试（33000 → 30000 → 27000），每步单跑一批。

P3b 农民冲锋时点前移 成本 ≈ 1 行　收益 中高　风险 中

现状COUNTER_FARMER_ATTACK_FRAME = 40500（27 分钟）。三个胜局里只有 cur11（42701 起手武器厂）享受到它；cur4 在 39114 帧就赢了，cur6 的武器厂起手在 44069 —— 农民令对赢得最快的两局完全没发挥作用。 攻略原文「11 分钟之后砍树的村民就没用了，可以调往前线集结，13 分左右所有农民都不必收集资源，可以当近战冲锋。（这一步我没有实现，所以没进 21000，只进了 22000）」 改法把 40500 降到约 21000~24000（14~16 分钟），或改为动态触发：当祭司距武器厂 < 30 格且敌方军队已清空时，立即释放农民。 风险中。农民全投入后经济停摆，一旦冲不下来就再无翻盘能力（而祭司死亡本身就直接判负，所以"保祭司"与"放农民"其实同一目标）。

P3c 复合弓量产时点 成本 ≈ 1 行　收益 待评估　需你拍板

现状COMPOSITE_BOW_MIN_FRAME = 22500（15 分钟前不训练复合弓兵）。 攻略原文「升时代后立刻研究复合弓和多靶场造兵……理想情况下，8 分多一点就可以两个靶场同时出兵，10 分钟前 3 个靶场同时出兵。」 差距8~10 分钟 vs 15 分钟。但：这条是你在 2026-09-06 明确要求的（"15min 前先不训练复合弓兵，避免被打死"），且当时的理由是"早期弓兵会被打死、白费食物 + 20 黄金"。 为什么现在可以重新讨论当时的前提是"祭司死了也没关系、先把经济做厚"。现在已确定祭司存活 = 唯一胜负开关，而攻略反复强调"保护好复合弓手"是核心。早期就有 6 个复合弓，第二波（13500）就能"无损过波次"，反攻也能提前。 建议不直接改常量，而是先跑一组"COMPOSITE_BOW_MIN_FRAME = 15000"的对照批。这是唯一一条有独立批次价值的。

四、攻略里不该照抄的部分

攻略作者是在写一个从零开始的 AI；我们这套已经跑了很久、沉淀了大量实测口径。以下 7 条照抄会引入倒退：

攻略建议为什么不照抄
map<int,int> farmer_state 记录村民工作 引擎的 tagFarmer 已经给了 NowState（空闲/移动/攻击/工作）、ResourceSort（手持资源）、WorkObjectSN（工作目标）、FarmerSort。另维护一份必然与引擎失同步（单位死亡/感化/重编号时 AI 侧不知道）。
我们已有的 huntingGroup / buildingFarmerType 是"AI 侧额外意图"（谁被打猎指派了、谁是建造者），颗粒度正确 —— 该记的才记。
「全局变量记录建设者 SN」 已有 buildingFarmerType（SN → FarmerType）承担同一职责，且能同时管多个建造者。
「每帧最多分配一次，不易冲突」 已按此实现。例：manageHunting() 末尾 return; // 每帧最多分配1个猎人。
「双人打猎效率最高」（需详细状态转换流程） 已实现且更简：每只瞪羚限 2 人（if (realCount >= 2) continue;），无需状态机。另"先建仓库再打猎、仓库选离死羚羊最近处"也已有 gazelleDropoffReady() 把关。

五、这与既有诊断的关系

此前记忆里对 N-2 的描述是：「感化档只判冷却 + 28 格不看血量 → 节流闸 return 全体短路 → 濒死逃命档轮不到 ⇒ 一次感化令冻结 150 帧」。

本轮证据把这条具体化并向前推了一步：

  • 「节流闸短路」成立，但它是果：真正致命的是 祭司为什么要在这时候起手 —— 因为第③档把"战车弓兵"列为合法目标，而感化距离（12）> 战车弓兵射程（7），起手即入网。
  • 被短路的"濒死逃命档"同样在 managePriest() 内部（第 2 步 pBR <= 0.25 强制撤退）—— 它排在感化档之后，且感化档 return 了。所以 3.5 秒内从满血到死亡期间，逃命档一次都没被执行。
  • 新增一条此前没有的判据：祭司的感化目标兵种 = 负局的预测因子（远程 → 死，武器厂 → 胜）。这条可以直接做成跑批后的自动体检项。
