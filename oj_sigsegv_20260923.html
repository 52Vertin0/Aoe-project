1.1 length 6, capacity 6 是这次最有价值的线索

std::vector 只在 size == capacity 时插入才扩容。源 vector 恰好处于 "已经装满、下一次 push_back 必然 realloc"的临界状态 —— 而 realloc 会 free 掉旧缓冲。AI 正在 memcpy 那块旧缓冲时，主线程把它释放了 ⇒ 读到已归还的内存 / 已 munmap 的 arena ⇒ SIGSEGV。

这不是"读到脏数据"，是"读到已释放内存"。gdb 能把 length/capacity 读成自洽的 6/6，恰好说明控制块（那三个指针）没被破坏，坏的是它指向的缓冲区 —— 教科书式的 UAF。

3 锁的责任划分：读侧有锁，写侧被注释

// GlobalVariate.cpp:1155  读侧 —— 有锁 ✓
tagInfo tagGame::getInfo() {
    QMutexLocker locker(&Locker);
    return *Info;
}

// GlobalVariate.cpp:1115  写侧 —— 锁被注释 ✗
void tagGame::update(tagInfo *newinfo) {
    // QMutexLocker locker(&Locker);//之前是严格的帧同步，现在改成严格的非帧同步
    ...
    Info = newinfo;
    if (openHunYao) {
        WLHHunYao(Info->buildings);      // ← 发布之后原地打乱这 7 个 vector
        WLHHunYao(Info->farmers);   ... WLHHunYao(Info->resources);
    }
}

写侧不是"忘了锁"，是"有意把锁交给调用方" —— 这也解释了为什么之前实测 「在 update() 里补一把非递归锁」会把游戏锁死：调用方 MainWidget::gameDataUpdate 已经先 tryLock() 了同一把非递归 QMutex ⇒ 同线程自锁死 （实测 rc=TIMEOUT、AITextLog 冻在 frame 1）。

3.1 我们本机的锁链是完整的

// MainWidget.cpp:2249  gameDataUpdate()
core->gameUpdate();                       // 锁外：只动 Map / Core，不碰 tagInfo ✓
if (!EditorMode) {
    const bool usrGameLocked = tagUsrGame.tryLock();
    if (usrGameLocked) {
        const bool enemyGameLocked = tagEnemyGame.tryLock();
        if (enemyGameLocked) {
            core->infoShare();            // ← 内部 Core.cpp:720/721 调 tagUsrGame.update() ✓ 持锁
            tagEnemyGame.release();  tagUsrGame.release();
            emit startAI();
        } else tagUsrGame.release();
    }
}

这段的注释写着「只有两个 AI 信息锁都获取成功时才同步数据」「如果第二把锁获取失败，必须释放已获取的第一把锁，避免后续 AI 永久停止」 —— 语气上是后来补的修复说明，不是原始代码。而 infoShare() 的开头正是 currentBuff[i].clear()（清空整块 buffer 再重填），没有这把锁就一定会踩到 AI 的深拷贝。

5 补丁：2 处改动，两种调用方式都安全

// ① GlobalVariate.h:254  —— 普通锁改成递归锁
-    QMutex Locker;
+    QMutex Locker{QMutex::Recursive};

// ② GlobalVariate.cpp:1117  —— 恢复写侧的锁
-   // QMutexLocker locker(&Locker);//之前是严格的帧同步，现在改成严格的非帧同步
+    QMutexLocker locker(&Locker);
调用方情形① + ② 之后的行为
已持锁（本机现状）update() 同线程重入 ⇒ 递归锁放行，不死锁；与 AI 的 getInfo() 互斥
未持锁（评测机）update() 自己上锁 ⇒ 与 getInfo() 互斥

关键点：必须用递归锁。上一轮试过只做 ② 而锁仍是普通 QMutex ⇒ 同线程自锁死 （rc=TIMEOUT、冻在 frame 1）。递归锁是让 ② 安全的前提，两处必须一起改。

QMutex(QMutex::Recursive) 在 Qt 5.9.2 就支持，不需要 Qt 5.14+ 的 QRecursiveMutex。

7 站内为什么修不了（第三面墙）

  • 提交边界只收 UsrAI.cpp + UsrAI.h ⇒ 碰不到 tagGame / MainWidget / Core
  • Info 与 Locker 都是 tagGame 的 private 成员 ⇒ UsrAI 拿不到锁
  • 没有"不加锁读取"的公开接口；而 tryLock() 之后再调 getInfo() 会自锁死（非递归 QMutex）
  • UsrAI 内严禁引用引擎新增符号（悬空 extern ⇒ undefined reference ⇒ 整个提交链接失败，比崩溃更严重）
⇒ 只要评测机跑的是无锁调用方的引擎，这个崩溃就无法通过"只提交 UsrAI.cpp/h"消除。 可行路径只有两条：(a) 评测方打 §5 的补丁；(b) 评测方升级到本机的 MainWidget.cpp 版本（含双 tryLock）。
