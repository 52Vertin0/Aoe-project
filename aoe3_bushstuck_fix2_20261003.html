上轮把「树 / 浆果 / 瞪羚 / 金 / 石」五类目标接进了「卡死 → 拉黑 → 换目标」闭环。 本轮的发现是：还有两条同形态的漏网路径 —— 大象和农场，它们既不记录目标、也不查黑名单， 所以村民在这两类目标上卡死时，兜底完全失效（和上轮浆果的病一模一样）。

两条推论
① 上限 3 vs 2 不是病根 —— 整整一局里从没出现 3 人同采一丛（最多 2 人）。 所以"主路径允许 3 人 / 冷路径 2 人"这个不一致在本局没有实际危害 ⇒ 降级为"待 A/B"，本轮不动。
② 21218 是凶手 —— 看它的派工时间点：f13 → f4236 → f4316 → f5329 → f7762， 五次派工，每一次都紧跟着一个村民从此沉默（末条指令分别是 f13 / f4238 / f4319 / f5331 / f7765）。

⇒ 这正好解释了为什么上轮的修复方向（拉黑正确目标 + 主路径查黑名单 + 真正复位重派）是对的： 只要 21218 被正确拉黑，主派工就会跳过它、把人送去别的丛。

大象那条为什么要单独说
大象本来有一套自己的拉黑（elephantBanUntil），但那是「凑不齐 4 人 → 主动召回孤兵」专用。 而 detectStuckGatherers 判定打象卡死时写的是 stuckResourceUntil —— 两套拉黑互不相通，所以"卡死拉黑"一旦对象是大象就完全打空，村民被重派回来继续送死。
这是铁律 26（同语义只写一遍）的典型违反：同一个概念（"这个目标暂时不要碰"）在代码里有两个各自为政的实现。

6. 下一局请重点看 [STUCK] 行

诊断行现在长这样：

[STUCK f=5817] 村民SN=41157 state=2 空手1579帧 目标SN=21218(资源) 在采1人 位置=(x,y) 距TC=8.3格 拉黑15000帧+待重派
字段怎么读
state1=WALKING（一直在走路 ⇒ 到不了）｜2=WORKING（在采但采不到 ⇒ 位置/容量问题）｜3=ATTACKING（真值见 config.h:228）
目标SN(类型)现在必须指向真正卡死的目标（上轮起已修），不再是张冠李戴的旧树
在采N人本轮新增的判据：卡死时该目标上已有几人。
若为浆果且 N≥2 ⇒ 坐实"满员超派"（那就该去统一 §1 里那个 3 vs 2）；
若 N=0~1 ⇒ 是"不可达 / 地形问题"，与容量无关
拉黑N帧资源 = 15000（10 分）；农场 = 900（36 秒）

判定修复是否起效的最简口径：同一村民若再次出现 [STUCK]，它的 目标SN 必须与上一次不同。
改前铁证是三次触发帧号严格等间隔（5817 → 7319 → 8822，间隔 1502/1503 帧）—— 那表示"完全没换目标"。
