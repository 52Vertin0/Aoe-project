2.2 逻辑：进展判据 + 两段脱困阶梯

// ① 进展判据（铁律 9：脱困动作绝不算进展）
if (dSiege > priestAdvBest + PRIEST_ADV_RESET_BL * BL) {      // 远出很多 ⇒ 场景已变
    priestAdvBest = dSiege; priestAdvBestFrame = frame; priestEscapeStage = 0;
} else if (dSiege < priestAdvBest - 0.5 * BL) {               // 真进展
    priestAdvBest = dSiege; priestAdvBestFrame = frame; priestEscapeStage = 0;
} else if (dSiege < priestAdvBest) {
    priestAdvBest = dSiege;                                   // 慢速蠕动：更新基准但【不】重置计时
}
const bool priestAdvStuck = (frame - priestAdvBestFrame > PRIEST_ADV_STUCK_FRAMES);

// ② 脱困阶梯（A ⇄ B 交替）
A 档：侧移 4 格绕开堵点（左右交替） → 下次仍卡则换 B
B 档：把祭司 2 格内的友军沿【侧向】推开 6 格（≤3 个）
       保命前提：仅当祭司 15 格内无活敌才清障（否则推开护卫=送祭司）
两档均：只重置"卡死计时"与"冷却"，绝不动 priestAdvBest

2.3 ★ 设计时排除的假阳性（关键正确性检查）

疑点：祭司抵达推进落点（距武器厂 11 格）后不再逼近 ⇒ 会被判"卡死"并开始侧移 —— 会不会误触发？
结论：不会。推进落点距武器厂 PRIEST_CONVERT_SIEGE_RANGE - 1 = 11 格，而 11 ≤ 12 = 感化射程 ⇒ 祭司一旦到达就命中上方的 感化分支（HumanAction(祭司, 武器厂)）并 return， 根本进不到 ADVANCE 分支。
⇒ ADVANCE 分支只在 dSiege > 12 时运行；在该区间内「120 帧未逼近 0.5 格」必然是物理卡死。
