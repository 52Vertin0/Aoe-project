上一轮的漏判（这是最关键的一条）

gsync 的做法是：name hiding 隐藏基类 ai.h:21-25 五个非虚 public 指令入口， 再用 find() 只读预检 ⇒ 命中有键 ⇒ 引擎构造里的 g_Object[key] 退化为纯查找。 这一步是对的，也有运行期证据（[INS-BAD] 累计丢弃 全批恒 0 ⇒ 没有削掉任何合法指令）。

但它只堵住了 UsrAI 这一半写者。引擎自带的 enemyai.cpp 里有：

enemyai.cpp：36 处直调 HumanMove(...) / HumanAction(...)
            ＋ 1 处 instruction(INS_CANCEL, …)

这些调用跑在 EnemyAI 线程，一样会执行 g_Object[SN]。 ⇒ 写者集合仍是 {主线程, EnemyAI 线程}，树仍被并发改。选手无法从自己的两个文件里关掉它。

给平台方的 5 行修法（语义等价，只是把 operator[] 换成 find） 
static inline Coordinate* g_ObjectRO(int sn) {
    auto it = g_Object.find(sn);
    return it == g_Object.end() ? nullptr : it->second;
}
把 GlobalVariate.cpp 那 5 行的 g_Object[SN] 换成 g_ObjectRO(SN) 即可。 注意 EnemyAI 侧也走同一批构造函数，所以改一处即覆盖全部。

为什么走 stdout 而不是引擎的 DebugText：7h 的 call_debugText 在 -exam 闸之后 ⇒ 我们的 [ENV]/[SNAP]/[INS-BAD] 文本在评测机上很可能被整条丢弃。 而 backtrace 里带着 gdb 自己的 stderr（could not find '.gnu_debugaltlink'） ⇒ 评测机捕获了进程输出 ⇒ fprintf + fflush 是唯一能被回读的通道。

⚠ 已踩的坑：GAME_VERSION 是 RuntimeConfig_GAME_VERSION() 返回的临时 std::string， 写成 const char* p = GAME_VERSION.c_str(); 就是 use-after-free —— 会凭空造一个假崩点。
