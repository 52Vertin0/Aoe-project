3  根因：加固被一次「整文件回退」覆盖掉了

09-23 就已经为这个崩溃写过自救（记忆里记为"已闭环"），但代码里现在找不到它了。用特征符号计数三版对比，一眼看出是哪一步丢的：

为什么"AI 线程直读"必然崩

// GlobalVariate.cpp —— 读侧有锁
tagInfo tagGame::getInfo() { QMutexLocker locker(&Locker); return *Info; }

// GlobalVariate.cpp —— 写侧【无锁】，locker 被注释掉
void tagGame::update(tagInfo *newinfo) {
   // QMutexLocker locker(&Locker);   ← 被注释
   ... Info = newinfo; WLHHunYao(Info->buildings); ...
}

// MainWidget.cpp —— 主线程只在 infoShare 期间持锁
tagUsrGame.tryLock(); core->infoShare(); tagUsrGame.release(); emit startAI();

① getInfo() 的锁只覆盖引擎自己那层拷贝；return *Info 把引用交出去后， 调用点（processData 的 info = ...）的深拷贝发生在锁外 ⇒ 与主线程 clear()/push_back() 的释放-重分配竞争 —— 拷贝到一半源块被 free ⇒ memcpy 读已释放页 ⇒ SIGSEGV （len=cap 正是"拷贝产物"的特征）。
② AI 侧无法靠加锁自救：tagGame::Locker 是私有成员碰不到；改用 tryLock()+getInfo() 会因 QMutex 非递归、同线程二次加锁而自锁死（实测整局冻在 frame 1）。

4  修法：只换「深拷贝发生在哪个线程」

AI 线程 postEvent(this)→ 主线程在 UsrAI::event() 里 getInfo()→ shared_ptr 发布→ AI 取走副本

UsrAI 由主线程创建（class AI : public QThread）⇒ postEvent 给它的自定义事件 由主线程事件循环派发；此刻主线程不在 infoShare() 内 ⇒ 读写同线程、天然串行， 不依赖任何引擎锁 ⇒ 与引擎版本 / NOWPLAYER / Buffer 尺寸全都无关。

★ 但原版是「每帧阻塞等待」—— 会腰斩胜率

原实现每帧都要 cond.wait(&st.mutex, 1000) 等主线程把 getInfo() 做完 ⇒ AI 的决策吞吐被主线程帧率钳死。同日干净对照（均为 map2×12 局、同批代码，仅"加固有无"不同）：

非阻塞版的三段逻辑

阶段行为开销
① 有新快照O(1) 取走；深拷贝在锁外（源由主线程独占产生，不可变）1 次深拷贝
② 没有新快照立刻沿用上一帧，同时顺手为下一帧投递请求 —— 绝不等待1 次深拷贝 + 1 次 postEvent
③ 从未拿到过仅开局第一帧真正 cond.wait 一次（1 秒上限，超时则跳过本帧）一次性

main:reuse ≈ 1:1 ⇒ 每 2 帧取到一份新数据，数据滞后 1 帧 = 40ms 游戏时间（不影响相对时序判断）
