旧逻辑：村民被派去一个到不了的浆果丛 → 卡 60 秒 → 兜底把它派回 TC → 它变成"卡在去 TC 的路上"（仍非 IDLE）

3. 为什么必须三处同改（不能只做 A+B）

这是本次最关键的一步推理，也是上次"先做 A+B+D 看看"会被判失败的原因：

只做 A+B：拉黑准确了、主路径也遵守了
  ⇒ 但【村民本身没有回到 IDLE】⇒ 主循环第 3 行 `if (f.NowState != HUMAN_STATE_IDLE) continue;` 照样跳过它
  ⇒ 它继续"卡在去 TC 的路上"，1500 帧后 STUCK 再次触发
  ⇒ 唯一变化：这次拉黑的是正确的丛 —— 可村民还是不动

结论：A+B 只解决"AI 下次别选那个坏丛"，不解决"这个村民已经动不了了"。 必须让 detectStuckGatherers 具备直接重派的能力 ⇒ 这就是 pendingRedispatch 存在的理由。

5. 跑一局怎么看（判读口径）

① 看 [STUCK] 行是否"不再等间隔复发"
改前铁证：同一村民三次触发帧号 5817 → 7319 → 8822（间隔严格 1502/1503 帧）＝打断无效的确定性判据。
改后应为：同一村民不再出现第 2 次等间隔触发；即使再触发，两次之间的目标 SN 必须不同。

② 看新增字段（本次诊断增强）
[STUCK f=… ] 村民SN=… state=3 空手1602帧 目标资源SN=21218 位置=(x,y) 距TC=8.4格 已拉黑+待重派
—— state 告诉你它卡在哪个状态（真值取自 config.h:228：0=IDLE / 1=WALKING / 2=WORKING / 3=ATTACKING； 因检测已排除 IDLE，这里必为 1/2/3 —— 2 或 3 = "正在采/打但采不到"，1 = 一直在走路，两者指向的病因不同），位置/距TC 告诉你它到底停在哪， 目标资源SN 现在能正确指向浆果丛而不是旧树 ⇒ 一次跑局即可定位"最初病因"（不可达 / 满员 / 被挤掉）。
