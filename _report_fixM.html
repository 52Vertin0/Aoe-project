2 · 先把口径校准对（本轮做对的三件事）

  • "转化率"的主体是祭司、客体是投石车（单位），不是武器厂（建筑）。 胜利条件仍是"祭司转换敌攻城武器厂"（唯一，无旁路）；而投石车 AT_STONE_THROWER 是敌方单位， 感化它的收益 = 得一辆射程 10 的我方投石车 ＋ 敌方减员。
  • flag 标定：ait 第 4 段 —— flag=0 我方 · flag=1 敌方 · flag=-1 引擎计分行（如"玩家 转换高级敌人，分数+8"＝人类玩家分数事件）。
    标定方法：用"祭司设置转换目标为…"这类必然属于我方的指令反推（祭司是 player[0]）。

4 · 路径 b 成功：fixM（W3 把投石车提到"远程军队"之前）

病根 —— 一个纯算术事实

pickByBlood 四档固定为 0 方阵兵 > 1 其余近战 > 2 远程军队 > 3 投石车（第 4 档） ⇒ W3 期间只要场上有近战 / 远程，祭司永不选投石车。这直接解释了"W3 段感化成功仅 10 次 / 反攻期 68 次"。

改动（UsrAI.cpp:1517，新增 12 行 / 删除 1 行）

int t;
if ((t = pickByBlood(0)) >= 0) return t;   // 0) 方阵兵       ← 保命档，不动
if ((t = pickByBlood(1)) >= 0) return t;   // 1) 其余近战     ← 保命档，不动
// ★★★ 2026-10-06 fixM：W3(第三波) 把投石车提到"远程军队"之前 ★★★
if (state == DEFENSE_WAVE3) { if ((t = pickByBlood(3)) >= 0) return t; }   // W3：投石车提前
if ((t = pickByBlood(2)) >= 0) return t;   // 2) 远程军队
if (state != DEFENSE_WAVE3) { if ((t = pickByBlood(3)) >= 0) return t; }   // 3) 投石车（非 W3 仍第四）

⚠ 保命档 0 / 1 不动：方阵兵与近战直接威胁祭司，而祭司死 ＝ 立即失败 ⇒ 保命优先级必须高于感化收益。
⚠ 仅 W3 生效：其它阶段（含反攻期）维持原序 ⇒ 符合用户"反攻期不限制"的要求。

7 · 判读边界与可沉淀的教训

  • ★ 教训 1（排序类改动的通用前置检查）：改"优先级 / 排序"前，先做"当前排序下该目标能否被选中"的算术检验。 fixM 的病根就是这条极简算术（第 4 档 ＋ 场上常有近战/远程 ⇒ 永不被选），一行排序可解，不需要加任何闸门。
  • ★ 教训 2（修法分类）："减少动作"（fixJ / fixL）在活锁与"对抗引擎"上无出路；"改排序 / 改落点"（fixK / fixM）代价小且可验证。 遇到"某行为收益低"时，先在选择顺序 / 落点上找解，最后才考虑加闸。
  • ★ 教训 3（判"能不能关掉引擎行为"）：先量指令的 Δ 间隔分布 —— 连续重发（Δ≤3）占绝对多数即说明 "这是引擎自动行为、AI 关不掉"，此时应立刻放弃该路径，转而改变使引擎触发该行为的前置条件（站位 / 距离）。
  • ★ 教训 4（护栏要覆盖"新行为可能带来的新风险"）：fixM 让祭司更早盯投石车，最大风险是"在 W3 火力下提前送死"， 因此护栏特意取"死在反攻起点前"这类针对性指标，而不是泛泛的"总祭死数"。
  • ★ 教训 5（口径自查）："恒 0 / 恒不变"的护栏要先当故障查；统计脚本必须自带"已知数据自校验"。
