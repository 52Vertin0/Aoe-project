「浆果采集者一直不动」—— 归因报告

2026-10-03 · 证据来源：实机日志 C:\new-aoe3.0.7g\AIText.log（mtime 10:21:21，一局 854 行 / frame 0→8866）· 源码 UsrAI.cpp 7317 行 md5 8432737 1（前 8 位）

TL;DR

不是村民"站住了"，是 AI 把它派出去之后就再也不管它了。
派工函数只服务 NowState == IDLE 的村民；村民一旦被派出去（状态变非 IDLE）又没能真正采到东西， 就掉进"既非 IDLE、也没有有效目标"的夹缝 —— 永久沉默。
唯一的兜底（每 1500 帧的卡死检测）三重失效：① 拉黑打错对象 ② 黑名单在主派工路径上根本没被查 ③ 打断动作不复位。
你说的"4 分钟"= 第一次 [STUCK] 触发在 frame 5817 = 3.88 分，此后每 60 秒复发一次。

2. 根因链（四层，每层带行号）

第 1 层 · 派工只认 IDLE，派出去就不回头

// assignIdleSimple()  :3157 —— 村民分配的【唯一】入口
// 它只遍历、并且只处理空闲村民；已被派工的村民不在候选里
// ⇒ 村民状态从 IDLE 变为"在途/工作中"的瞬间，它就脱离了 AI 的管理

这是设计使然、并非 bug。问题在于它假设"被派出去 = 最终会采到" —— 而实测有 4 个村民没采到、也没人管。

缺陷 C：打断动作不复位 ⇒ 严格 60 秒周期复发

41157 的三次 [STUCK]： f=5817 → f=7319 → f=8822     间隔 = 1502 / 1503 帧（≈ 严格 1500 + 处理延迟）

// 打断只有这一句：

gatherStuckFrame.erase(f.SN);      // :7175 计时清零 → 重新累积 1500 帧

⇒ 如果这次"打断"真的让村民回到可被重新调度的状态，第二次触发应该【不再发生】。
  实测三次严格等间隔、症状毫无改善 ⇒ 村民状态根本没有被复位，
  只是把计时器清零、让它再卡 60 秒。这就是"一直不动"的直接来源。
