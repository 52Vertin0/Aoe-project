你的日志报的是 79:25：行号、错误文案、trigraph 的行分布全部一致（差 1 列 = 编译器版本 5.3 vs 你那边更新的 GCC 在列号/插入符上的差异）， 三元字警告里 1973:62 与 E/D 完全同列。中文变 ? 的具体路径落在"逐字符 ~ 逐字节"之间（58 / 60 / 73），不影响结论，也不影响修法。

为什么一行行尾能炸出 expected ')'

仓库（正常 CRLF）：
 39 | #define FARM_WOOD_NEED(gazelleStockBuilt) \      ← \ 告诉预处理「下一行还是本宏」
 40 |     ((gazelleStockBuilt) ? BUILD_FARM_WOOD : (…))

被写成 \r\r\n 之后：
 39 | #define FARM_WOOD_NEED(gazelleStockBuilt) \ + CR   ← \ 吞掉第一个 CR 后，宏定义在此结束
    |  + CR         ← 紧跟的这个 CR 又是一次换行（空行）
 40 |     ((gazelleStockBuilt) ? …)                    ← 宏体掉到文件作用域
     ⇒ 文件作用域看到 `((gazelleStockBuilt)`：GCC 按「带括号的声明符」解析，
       括号里的名字不是类型、接着又来一个 `?`  ⇒ error: expected ')' before '?' token

同理，\n\n（每行插空行）也会把宏体与宏定义拆开，错误完全一样。区别只在表现形式，判据都是行号翻倍。

3 元凶：write_text() 的二次换行翻译

D:\deepseek\optimize_new_aoe_20260921\apply_safe_slim.py 末尾：

# 写 CRLF + UTF-8 no BOM
out_cpp.write_text(cpp.replace("\n", "\r\n"), encoding="utf-8")   ← 这里
out_h.write_text(h.replace("\n", "\r\n"), encoding="utf-8")
  • read_text(encoding="utf-8") 默认 newline=None ⇒ 读进来时 \r\n 已归一成 \n（没问题）。
  • 手工 .replace("\n","\r\n") 拼出 CRLF（也没问题）。
  • write_text() 默认又是 newline=None ⇒ 写出时把每个 \n 再翻成 \r\n ⇒ 已有的 \r\n 变成 \r\r\n。就是这一步。
修正（2026-09-22 23:35）：这条只修了一半。同目录 apply_safe_slim2.py:65 与 apply_l2_count.py:41 / apply_l2_nearest.py:70 确实都已改成
with out.open("w", encoding="utf-8", newline="") as f: f.write(cpp.replace("\n","\r\n"))
但第 1 版 apply_safe_slim.py:67-68 原封未动 —— 任何仍调它的流程会再次产出 \r\r\n。本轮已把它一并修掉（写、读两处都显式 newline=""）。
它为什么能溜到编译才炸：紧随其后的自检 read_text(encoding="utf-8") 也默认 newline=None， universal-newline 把 \r\r\n 归一成 \n ⇒ 打印出来的 count("\r\n") 完全正常，自检形同虚设。
修复实证（同内容、两种写法、看落盘字节）：旧 write_text ⇒ \r\r\n=199；新 open(newline="") ⇒ \r\r\n=0 / \r\n=199。
规则固定：任何"手工拼 CRLF"的写法，写文件时必须带 newline=""；更省事的做法是全程 read_bytes()/write_bytes()。

3.1 环节确证（2026-09-22 23:59）：损伤发生在「网站提交」那一步

用户确认：那份日志是通过网站提交、在评测机上编译产生的。这解释了本机为什么全盘扫不到坏副本 —— 坏掉的是提交到网站之后、落到评测机磁盘上的那一份。

服务端收下文本后几乎一定会做一次「补 CR」，两种最常见实现都踩同一个坑：

服务端行为提交 CRLF 源（现行做法）提交 LF 源
A. content.replace("\n","\r\n") 后落盘\r\r\n × 6342正确 CRLF
B. Windows text-mode open("w")（每个 \n 前补 CR）\r\r\n × 6342正确 CRLF
C. unix2dos（LF → CRLF）视实现而定正确 CRLF
D. 原样二进制保存原样 CRLF纯 LF（GCC 一视同仁）
⇒ 提交纯 LF 源，四种服务端行为全部免疫。

唯一致命点只有一处续行。全文件 6342 行里，行尾反斜杠（\ ＋ 换行）只有 1 处 —— 第 39 行 #define FARM_WOOD_NEED(gazelleStockBuilt) \；UsrAI.h 里 0 处。 \r\r\n 的其余后果（行号 2N−1）对编译无害，唯独切断这一条续行才会炸出 error: expected ')' before '?' token（报在"79 行"＝真实第 40 行，正是宏体那行）。

4 第二个损伤：中文被吃成 ?

日志里约 60 条 trigraph ??= / ??( / ??) / ??- / ??/ / ??< 警告，只可能来自真实的 ??X 字节。 仓库源的 118 个 ? 全部在 a ? b : c 与格式串 %1 里，零处 ??X。⇒ 那份副本的中文被替换成了 ?（UTF-8 的中文被逐字符/逐字节吃掉）， 两个 ? 恰好挨到 = ( ) - / 就构成三元字。

影响说明
不影响编译成败三元字在 C++11 起默认不翻译（所以才只是 warning），字符串里的 ? 照原样保留。
但会毁掉日志可读性所有 DebugText("…中文…") 的标签会变成 ?。我们的观测口径大量依赖 [TAG]（ASCII，能活）+ 中文短语（会死）， 一旦这种副本进了实机，ait 日志的中文判据全部失效。

当前核验（逐字节）：D:\deepseek\optimize_new_aoe_20260921\ 下 UsrAI_pre/slim/opt/opt2.cpp、baseline/、slim/ —— 全部纯 UTF-8 + 统一 CRLF + 孤立 LF=0 + 三元字=0，且四个臂都 rc=0 / errors=0 / write-strings=16（与基线同形）。所以那个 ? 化发生在已被覆盖的中间态，现在的链路不自带该损伤。
