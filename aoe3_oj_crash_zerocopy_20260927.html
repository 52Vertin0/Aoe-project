AOE3 UsrAI · 2026-09-27 17:0x · UsrAI.cpp 1aecc386·6891 / UsrAI.h 1f9c61872·442

结论加固"换线程"能解决第一次崩溃，但解决不了同一个目标对象

第二次 backtrace 的崩溃点从 processData 挪到了 refreshSnapshot，但函数栈末端完全相同 —— 都是往同一个成员做 vector<tagBuilding> 深拷贝。 两次崩溃源不同、目标相同 ⇒ 根因是"这个目标的缓冲不可信"，与"谁在写源"无关。所以本次把该成员从「值 + 反复深拷贝」改为「shared_ptr 直达、全程零拷贝」，让这条崩溃路径在结构上消失。

三、修法：零拷贝快照

1. 数据结构改造（核心）

// UsrAI.h —— 原： tagInfo info;   （值成员，被反复深拷贝）
std::shared_ptr<tagInfo> infoPtr;   // ★ 快照由主线程 new、AI 线程独占持有

// UsrAI.cpp refreshSnapshot()：三处深拷贝全部换成只换指针
- dst = *fresh;              // 写旧缓冲 ⇒ 崩溃点
+ infoPtr = fresh;           // O(1)，引用计数原子 +1
- std::shared_ptr<tagInfo> cached = st.lastGood;  dst = *cached;
+ if (infoPtr) { st.reuseCount++; return true; }  // 沿用上一帧，连指针都不换

访问方式：info.xxx → infoPtr->xxx，共 400 处按 \binfo\. 词边界脚本替换。改前已验证四项、零误伤：无 ->info.、无字符串字面量、无同名局部变量、无前缀粘连（[A-Za-z_0-9]*info. 计数全是裸 info.）。

2. 完整性哨兵（配套防线）

static bool snapshotLooksSane(const tagInfo& t) {   // 全 O(1)：只做指针相减，不解引用任何元素 ⇒ 自身绝不能崩
    const size_t LIM = 20000;
    return t.buildings.size()       <= LIM && t.farmers.size()         <= LIM
        && t.armies.size()          <= LIM && t.enemy_buildings.size() <= LIM
        && t.enemy_farmers.size()   <= LIM && t.enemy_armies.size()    <= LIM
        && t.resources.size()       <= LIM && t.exploredUpdate.size()  <= LIM * 8;
}

在 event() 发布前检查；不合理则丢弃本次、AI 沿用上一帧（最坏钝 1 帧）、累计 badSnapCount。被踩坏的数据典型特征就是 size() 变天文数字 —— 不拦的话后续任何迭代/深拷贝立刻 SIGSEGV。

3. 防御层

~UsrAI() { stopThread = true; condition.wakeAll(); wait(); }   // 派生类侧先停线程（~AI() 的 wait 太晚）

② NOWPLAYER≥3 时本机必崩（已复现）—— 但不是本次原因
